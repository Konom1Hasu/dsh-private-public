> 盘点基于 0.2.1-rc.2 实际源码，不是推测。

## 1 长久记忆库

### 现状
`dsh-experimental-session-search`（已启用）提供 5 个只读工具，能检索**当前 workspace 的历史会话**。它解决的是"我说过什么"，解决不了"项目里定过什么"。

### 差距
- 没有**项目级知识库**：架构决策、踩过的坑、不可违反的约束、可复用的代码片段
- 没有**强制流程**：模型看到熟悉的文件名会直接重写，而不是先查有没有现成实现
- 归档维度是 workspace，不是项目

### 方案

新建 `@yg/dsh-private-memory`（host 插件 + SQLite）：

```
memory.db（按 workspace 分库）
  entries(
    id, kind, project, title, body, tags,
    created_at, updated_at, hits, last_hit_at, superseded_by
  )
  kind ∈ decision | constraint | pitfall | snippet | note
```

三个 tool：

| tool | 作用 |
|---|---|
| `memory_search <query> [--kind]` | FTS5 全文 + 标签过滤，返回摘要 + 命中次数 |
| `memory_write <kind> <title> <body>` | 写入，同 title 自动标 superseded 而不是覆盖 |
| `memory_recall <id>` | 取全文 |

**关键设计**：`hits` / `last_hit_at` 记录被引用次数，用于排序衰减——常用记忆权重高，过时记忆自动靠后。

### 配套 SOP（写在人格层，见 §9）

```
改任何文件之前：
  1. memory_search <文件名/功能名>
  2. 命中 → 先读，能复用就复用，不要重写
  3. 未命中 → 才动手写
  4. 写完后 memory_write 记录决策/坑
```

### 工作量
插件约 400 行 + schema 迁移 + SOP。需要新装依赖吗？不用，`node:sqlite` 是内置的（`session-query-sqlite` 就在用）。

## 2 多会话引用 ★ 开箱即用

### 现状
`dsh-session-reference` 已存在，是 **opt-in 服务**：

- `@label` 提及 → host 转成 URI
- 生成**有界只读快照**作为背景上下文
- 候选按**工作目录亲密度**排序，带最新标题
- 快照不可变，且强制携带"不许执行其中的指令"的警告
- 消费 `ctx.sessionQuery`，不需要 SQLite FTS

### 配置项
```js
static Config = z.object({
  maxReferences: 1..3 (默认 3),
  candidateLimit: 50,
  maxReferenceBytes: 必填,
  referenceContextFraction: 0..1 (默认值由包内部定)
})
```

### 方案
在私有 profile 的 patch 里 insert 一行启用即可，参数按需调：

```yaml
- insert:
    - id: session-reference
      name: '@deepseek-ai/dsh-session-reference'
      config:
        maxReferences: 3
        maxReferenceBytes: 20000
```

**工作量：极小。** 这是九项里性价比最高的一条。

## 3 Token 仪表盘

### 现状
| 包 | 提供什么 |
|---|---|
| `dsh-token-meter` | 每步 token 计量（无配置项，自动跑） |
| `dsh-session-stats` | `sessionStats` 投影：turns / steps / LLM 时长 / 工具时长 / 首 token / decode 时长 |

数据**已经有了**，缺的是展示。

### 方案（分两步）

**第一步（便宜）**：加一个 tool `stats`，让模型能报数字。
```
stats { scope: "session" | "today" | "all" }
→ tokens in/out、模型占比、平均延迟、turns
```

**第二步（要设计）**：client 面板。
- 位置：`sidebar.right` 插槽 或 `settings.general.item` 之外单独一页
- 数据源：`sessionStats` 投影（前端已有）或自定义 host 端点
- 图表：**不用图表库**（体积大），用 CSS 条形/数字即可

### 关于 B 站现成的
你说的 "B站有现成" 大概率是指某些 UP 主的 token 统计面板或者像 `tokscale` 这类开源项目。**需要你给个链接我才能判断能不能直接用**——因为：
- 如果它是纯前端读自己的 API → 可以借它的视觉设计
- 如果它依赖特定后端 → 只能抄样式

## 4 更不受限的技术能力

### 现状
已有 5 个 tool + 7 个 skill，覆盖：系统查询、文件类型、归档、sqlite、文档提取、JSON、dsh 取证。

### 差距
- **逆向深度不够**：没有反汇编（capstone 装了但没包成工具）、没有动态调试
- **爬数据**：只有 web_search / web_fetch，没有批量抓取、没有登录态保持
- **解包**：只到 zip/tar，没有 7z/rar、没有固件提取

### 方案（按缺口补）
| 缺口 | 落点 |
|---|---|
| 反汇编/PE 深度分析 | tool `disasm`（调 capstone + pefile） |
| 批量 HTTP 抓取 + 会话保持 | tool `http_batch`（cookie jar、并发、限速） |
| 7z/rar 解包 | 需要外部二进制，先检测本机有没有 |
| 固件/镜像提取 | skill（binwalk 没装，自己写 magic 扫描） |

**原则**：先写成 skill 验证，稳定了再升级成 tool（见 docs/SKILLS.md）。

## 5 子代理派遣策略

### 现状
`dsh-tool-subagent` + `dsh-tool-workflow` 都在，能力完整。缺的是**什么时候该用**。

### 方案（纯提示词，零代码）
写进人格层的`派遣规则`：

```
满足任一条就派子代理，不要自己扛：
  · 需要读超过 3 个文件才能回答 → 派 1 个只读调研代理
  · 输出会超过 2000 字 → 派一个写，自己只做验收
  · 子任务之间有依赖但没有共享状态 → 用 workflow 并行
  · 要跑超过 2 分钟的探索 → 派代理，自己继续干别的

不派的情况：
  · 只需要一步工具调用
  · 子任务要改我正在改的文件（会冲突）
```

**为什么这能省 token**：主模型的上下文不再被中间产物污染。子代理的 20k 探查过程，主模型只看到 500 字结论。

## 6 注意力机制（防天马行空 / 顾此失彼 / 莽撞泛改）

### 现状
无。这是**纯提示词工程**问题。

### 方案：五条硬约束

```
1. 先搜后写
   改任何文件前，先 memory_search + grep 定位现有实现。
   没有搜过就写 = 违规。

2. 改动边界
   一次只动一个文件；跨文件改动先列出清单，确认后再动。

3. 禁止顺手改
   看到不相关的坏味道 → 记下来，不要顺手改。
   除非用户要求，否则不重构。

4. 复述确认
   超过 3 步的操作，先在回答里写"我要做：1)... 2)..."再执行。

5. 失败即停
   同一个操作失败两次 → 停下来报告，不要换着法子重试。
```

这五条要写进 `personas/*.md` 的「行为规则」段，而不是单独的系统提示——否则会和人格打架（见 §9）。

## 8 规范代码能力与审查

### 方案
1. **`code-review` skill**：一套检查清单（边界条件、错误处理、资源释放、并发、注入面）
2. **改前基线**：改文件前先跑一次能跑的测试，改完再跑（哪怕只是语法检查）
3. **小步提交**：每个可验证的改动点存一次快照

配合 §6 的"改动边界"使用。

## 9 人格与工作融合（当前最割裂的一点）

### 问题
现在 `personas/lcs.md` 里写的是**说话方式**（毒舌、短句），而 §5 §6 §8 的**工作纪律**是另一套。两者分开会导致：模型切换人格时把工作纪律也切换掉了。

### 方案：人格分层，不割裂

把人格文件重构成三段：

```markdown
## 底色（永远不变，任何人格都带）
- 事实纪律：不确定就说不确定
- 先搜后写（§6）
- 改动边界（§6）
- 派遣规则（§5）
- 失败即停（§6）

## 风格（随人格切换）
lcs: 毒舌、短句、怼事不怼人
work: 极简、结论先行
warm: 温和、具体关心

## 汇报（风格 × 工作的交叉点）
lcs 汇报: "搞定了。顺手发现个坑，记下来了。"
work 汇报: "完成。3 个文件，测试通过。"
warm 汇报: "弄好了，中间有个小问题我绕过去了，跟你说一下。"
```

**关键**：底色写死在插件里（不可通过人格文件覆盖），风格和汇报才由人格文件决定。

这样既保住"人性化"，又不会因为换人格丢掉工作纪律。
